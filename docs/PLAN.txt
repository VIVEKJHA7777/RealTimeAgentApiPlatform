PART 1. WHAT ARE WE BUILDING? (IN ONE MINUTE)
---------------------------------------------------------------------

We are building ONE website + ONE backend server that many brands
can share.

  - A brand signs up on our website.
  - The brand uploads its product data (a CSV file, e.g. sku + price).
  - The brand creates an "API" with a few clicks (no coding).
  - Our website gives the brand:
        1. an API URL      (where to call)
        2. an access token (the secret key that proves who is calling)
  - The brand pastes these into BrandStore Studio -> Real Time Agent.
  - Now Jivox can call our API and get LIVE prices for that brand.

All brands use the SAME server. Their data never mixes.

Why we need it: to test the Jivox Real Time Agent we need a real,
public API that answers in the exact "contract" format. This project
gives us that API, and it teaches us backend + frontend + database +
security along the way.


---------------------------------------------------------------------
PART 2. THE MOST IMPORTANT QUESTION
        "When Jivox calls us with a token, how do we know which
         brand it is?"
---------------------------------------------------------------------

Short answer: THE TOKEN ITSELF TELLS US.

Every token we create is saved in our database next to the brand
(and the API) it belongs to. When a call comes in, we look the token
up, and the database row tells us the brand.

Think of it like a hotel key card:
  - Reception (our website) makes a card for Room 204 (Brand A).
  - The card does not have "Room 204" printed on it, but the door
    system knows which room the card belongs to.
  - If you lose the card, reception cancels it and makes a new one.

2.1  STEP-BY-STEP FLOW (from sign-up to a live price in chat)
---------------------------------------------------------------------

 STEP 1  Brand signs up on OUR website
         "Acme Shoes" creates an account and an organization.

 STEP 2  Brand uploads data
         Acme uploads products.csv:
             sku,       price,  category
             SKU-1001,  79.99,  shoes
             SKU-2049,  129.00, shoes
         Acme tells us: "sku is my unique id column".
         We save every row in our database, tagged "belongs to Acme".

 STEP 3  Brand creates an API (with clicks)
         Acme picks:
             - which dataset      : products
             - which fields to return : price
             - the method         : GET  (POST later)
         We save this as an "API config", tagged "belongs to Acme".
         We show Acme its URL, for example:
             https://our-platform.com/v1/acme-shoes/live/prices

 STEP 4  Brand generates an access token
         Acme clicks "Generate token". We create a long random secret:
             rtk_8Hf2k...Q9zP     (about 40 random characters)
         - We SHOW it to Acme ONE TIME only.
         - We SAVE only a scrambled version of it (a "hash"),
           plus a note: "this token belongs to Acme, API = live/prices".
         - Even if someone steals our database, they cannot get
           the real token back from the hash.

 STEP 5  Brand goes to BrandStore Studio (Jivox)
         Data Sources -> Real-time data -> Add Real Time Agent
         - selects the fields (e.g. current_price)
         - pastes OUR token as the "standing service token"
         Jivox stores the token safely in its parameter store.

 STEP 6  The contract is written (by the Jivox author agent)
         The contract tells Jivox how to call us:
             base_url             : https://our-platform.com/v1/acme-shoes
             path                 : /live/prices
             service_header       : X-Api-Key
             service_value_format : {token}
             query                : ids = {item_id}
         So Jivox will send our token in the "X-Api-Key" header.

 STEP 7  Jivox verifies the contract (one test call to us)
             GET /v1/acme-shoes/live/prices?ids=SKU-1001,SKU-2049
             X-Api-Key: rtk_8Hf2k...Q9zP
         We answer correctly -> contract becomes "verified".
         Then it is activated in Studio.

 STEP 8  Real use: a shopper asks ChatGPT about Acme shoes
         Jivox calls us again with the current product ids,
         we return live prices, Jivox shows them to the shopper.

---------------------------------------------------------------------
2.2  WHAT HAPPENS INSIDE OUR SERVER FOR EVERY CALL
---------------------------------------------------------------------

 Incoming:  GET /v1/acme-shoes/live/prices?ids=SKU-1001,SKU-9999
            X-Api-Key: rtk_8Hf2k...Q9zP

  1. Read the token from the X-Api-Key header.
       No token?                    -> 401 Unauthorized. Stop.

  2. Scramble (hash) the token the same way we did when we made it,
     and search the tokens table for that hash.
       Not found / cancelled?       -> 401 Unauthorized. Stop.
       Found -> the row says: brand = Acme, api = live/prices.
       >>> THIS IS HOW WE KNOW WHICH BRAND IT IS. <<<

  3. Double-check the URL matches the token.
       URL says "acme-shoes" + "live/prices".
       Token says Acme + live/prices.        -> OK, continue.
       If Brand B's token is used on Acme's URL -> 403 Forbidden.
       (So one brand can never read another brand's data,
        even if it guesses the URL.)

  4. Read the ids: "SKU-1001,SKU-9999" -> ["SKU-1001", "SKU-9999"]

  5. Search the database:
       "products WHERE brand = Acme AND sku IN (SKU-1001, SKU-9999)"
       The "brand = Acme" part is ALWAYS added. This is the
       wall between brands.

  6. Build the answer in the exact contract format:
       {
         "status": "success",
         "generated_at": "2026-10-09T10:00:00Z",
         "data":   [ { "sku": "SKU-1001", "price": 79.99 } ],
         "errors": [ { "error_id": "SKU-9999",
                       "error_code": "NOT_FOUND",
                       "error_message": "unknown sku" } ]
       }

  7. Add the header  Cache-Control: no-store   and send it.
     Whole thing must finish well under 3 seconds.

  8. Write a small log line (time, brand, ids count, status).
     NEVER write the token itself in logs.

---------------------------------------------------------------------
2.3  WHY BOTH A TOKEN AND A BRAND NAME IN THE URL?
---------------------------------------------------------------------

  - The TOKEN is the real proof of identity. It is secret.
  - The URL (/v1/acme-shoes/live/prices) is just an address.
    Anyone can see it. It is NOT proof of anything.
  - We keep the brand name in the URL because it makes logs and
    debugging easy to read, and Jivox needs a fixed base_url
    anyway. But we always trust the token, never the URL.

---------------------------------------------------------------------
2.4  TOKEN RULES (SECURITY, IN SIMPLE WORDS)
---------------------------------------------------------------------

  - Token is long and random (cannot be guessed).
  - Starts with "rtk_" so a human can recognise it as our token.
  - Shown once. If lost, generate a new one.
  - We store only the hash, never the real token.
  - A brand can cancel ("revoke") a token any time. A cancelled
    token stops working immediately.
  - One token belongs to one brand. (Later: one token per API.)
  - Never put the token in the URL. Only in the header.
  - Never print the token in logs or error messages.

---------------------------------------------------------------------
2.5  OPEN QUESTION FOR YOU (please decide)
---------------------------------------------------------------------

  Should one token open ALL of a brand's APIs, or only ONE API?

    Option A - one token per brand (simpler)
        Easy to manage. But if leaked, all that brand's APIs open.
    Option B - one token per API (safer)
        Matches Jivox nicely: one Real Time Agent = one API = one
        token. A leak affects only that API.

  My suggestion: start with A in Phase 5 (simpler to learn),
  switch to B in Phase 8 when we build the real-time features.

PART 3. TECH STACK
---------------------------------------------------------------------

 Frontend (the website brands use)
   - React + TypeScript
   - Vite            (fast dev server / build tool for React)
   - React Router    (pages)
   - Tailwind CSS + shadcn/ui (styling and ready-made components)

 Backend (the server that does the work)
   - Node.js + Express + TypeScript
   - Prisma          (talks to the database in TypeScript)
   - PostgreSQL      (the database)
   - Zod             (checks that incoming data is valid)

 Tools
   - Docker Compose  (runs PostgreSQL on our laptop)
   - Git + GitHub
   - ngrok or cloudflared (temporary public URL so Jivox qa3 can
     reach our laptop, until we deploy properly)

 Not now (later, only when needed): Redis, BullMQ, cloud storage,
 automated tests.


---------------------------------------------------------------------
PART 4. HOW THE PIECES TALK TO EACH OTHER
---------------------------------------------------------------------

   Brand's browser
        |
        v
   React website (localhost:5173)
        |  /api/*  (Vite forwards these to the backend)
        v
   Express server (localhost:4000) <------ Jivox calls /v1/*
        |                                  with X-Api-Key token
        v
   PostgreSQL (Docker, localhost:5432)

 The Express server has TWO doors:
   /api/*  -> for our website. User must be logged in (cookie).
   /v1/*   -> for outside callers like Jivox. Needs a token.

 There is only ONE server for all brands. Every database row has a
 "brand id" (organizationId), and every query filters by it.


---------------------------------------------------------------------
PART 5. DATABASE (FIRST VERSION, PLAIN WORDS)
---------------------------------------------------------------------

  users          - people who log in (email, hashed password)
  organizations  - brands (e.g. Acme Shoes, slug "acme-shoes")
  (no memberships table: one account = one brand, via organizations.owner_id)
  sessions       - who is logged in right now (for the website)
  projects       - a brand's workspace (a brand can have several)
  datasets       - an uploaded file's info: name, id column, columns
  records        - one row per product:
                     brand id, dataset id,
                     external_id  (e.g. "SKU-1001"),
                     data         (the rest of the row as JSON:
                                   { "price": 79.99, "category": "shoes" })
  api_configs    - (Phase 6+) the API a brand built with clicks:
                     path, method, dataset, id field, response fields
  api_tokens     - token hash, brand id, (later) api id,
                     first 8 chars for display, created, revoked

 Why "data as JSON" instead of fixed price columns?
   Every brand's CSV looks different. JSON lets us store any columns
   without changing the database for each brand.

PART 7. WHAT WE ARE NOT DOING NOW (AND WHY)
---------------------------------------------------------------------

  Redis / cache       - database is fast enough for small data
  Background jobs     - small CSV files upload fine directly
  Roles / invites     - removed: one account = one brand (ROADMAP D7)
  API versions        - nobody depends on our API yet
  "user" tokens       - Jivox says this comes later
  Rate limits         - no real traffic yet
  Automated tests     - your choice; we keep code easy to test later
  Contract checking   - Jivox does the checking; we only answer right
